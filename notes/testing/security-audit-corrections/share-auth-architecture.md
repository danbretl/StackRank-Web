## SR-01 and SR-04

SR-01 is supported: the Movies table-level anonymous grant exposes `list_id`, and its active-row SELECT policy also exposes foreign owners' identifiers to authenticated callers. Dogs already excludes those columns for anonymous reads. No private ranking-row disclosure was demonstrated.

The audit's statement that no unlisted intent was found is incomplete. `CLAUDE.md:306` explicitly says `/s/` is excluded from indexing because links are **unlisted snapshots**. Publicly accessible and unlisted are compatible: a visitor need not sign in, but must supply the exact link. Existing noindex markup supports this intended discovery model, although noindex alone does not enforce it. Implementing exact-slug lookup follows that established intent; reclassifying snapshots as deliberately enumerable would require a separate product decision.

The implementation is `supabase/migrations/20261009052514_restrict_public_shares_to_exact_slug.sql`, generated by the local Supabase migration CLI. It makes no row changes:

- `read_movie_share(share_slug text)` returns only `slug`, the allowed top-level Movies payload fields, and `updated_at` for the exact active 10-character slug.
- `read_dog_share(share_slug text)` returns only `slug`, `category`, allowed top-level Dogs payload fields, `created_at`, and `updated_at` for the exact active 12-character Dogs slug. Other categories cannot be read through this function.
- Both functions are static SQL, `SECURITY DEFINER`, with empty `search_path`, fully qualified tables, explicit revocation predicates and no optional/list/predicate arguments. Their primary-key equality yields at most one row. Null, malformed, unknown or revoked slugs return no rows.
- Default PUBLIC function execution is revoked; `anon` and `authenticated` receive explicit EXECUTE. The deliberate public lookup cannot require `auth.uid()` because signed-out access is a product requirement. No owner identifier is returned. Historical extra top-level Movies payload keys are projected out without changing the stored snapshot; nested published item content is not newly schema-filtered here.
- Anonymous and PUBLIC table **and column** SELECT grants are removed. Removing only a table grant would leave the existing Dogs column grants intact. The two public-read RLS policies are removed. Existing authenticated owner-only SELECT and mutation policies/grants remain, including revoked-row management and all current `list_id` filters.

The intended function owner must have the required underlying reads, as the normal migration owner does. Before live execution, review actual function collisions, roles/inheritance, table/column grants and policies using metadata only. Unexpected additional broad policies or inherited grants must be resolved explicitly, not assumed absent. Native synthetic tests are required before approval. Hosted PostgREST schema-cache and role behavior remain a separate verification boundary.

## Deployment and cached clients

Use one transactional database cutover **after** deploying and verifying RPC-capable anonymous viewers. Those viewers may fall back to the old table endpoint only for the precise missing-function `PGRST202` deployment condition. Permission failures, unknown links, malformed rows and arbitrary network errors must not trigger fallback. The pre-migration compatibility window remains enumerable and must not be reported as fixed.

After the exact SQL is approved and applied, the RPC works and direct anonymous enumeration fails. Existing URLs, slugs, published snapshots and owner publish/update/revoke flows remain unchanged; visitors acquire no login requirement. Already-loaded old viewers that still issue direct table requests must reload. Cache/version updates ensure fresh page loads receive the corrected reader. There is no indefinite compatibility between arbitrary old direct-table access and genuine unlisted enforcement: retaining the old permission as a fallback would retain the finding. Known previously obtained links still grant access until the owner revokes them; this correction cannot retract copies already collected.

No new rate-limit guarantee is claimed. The lookup rejects listing and arbitrary predicates, but repeated exact-slug guesses remain technically possible. Slugs are existing random bearer capabilities, not account authentication. Do not rotate existing slugs to claim stronger secrecy.

After cutover, rollback should retain an RPC-capable viewer or roll forward its defect. Deploying a pre-RPC viewer would break reads. The separate `share-rollback.sql` records an emergency compatibility rollback for review and disposable fixture testing. It reinstates the old table grants/policies, deliberately reopening enumeration and owner exposure, and therefore requires separate explicit approval of that exact security regression; it is not an automatic rollback. It keeps the RPCs for newer viewers. Snapshot rows and owner settings need no restoration because neither forward migration nor rollback modifies them.

## SR-07

The local source includes a team-scoped preview wildcard, localhost and plain-HTTP LAN redirects, plus the retired GitHub Pages URL. The audit did not establish a hostile admitted host or query the hosted allowlist. Its helper tests reject query/hash-controlled external redirects. Classify the finding as conditional hardening, not demonstrated account takeover.

Recommended exact production settings proposal: retain site URL `https://www.stackrankapp.com/movies`; retain only the six explicit HTTPS root/Movies/Dogs URLs on `www.stackrankapp.com` and `stackrankapp.com` in the additional list. Remove preview wildcard, retired GitHub Pages, localhost and LAN entries from the **production** allowlist after exact-action confirmation. Development needs its own explicit environment/configuration; do not create a project or change credentials as part of this proposal. Checked-in config changes alone do not change hosted Auth. Verify hosted metadata before and after approval, without printing provider secrets or accessing customer records.

Current correction disposition: leave Auth configuration and flow unchanged. The hosted allowlist and admitted-host exploit prerequisite have not been verified; removing entries now would interrupt known development/preview workflows without evidence that those workflows have a replacement. The narrower six-URL set above is a concrete future approval proposal, not an applied fix or a pending automatic deployment step. SR-07 remains explicitly conditional hardening.

Do not silently change the current email/OAuth flow to PKCE in this correction. Supabase documents that the verifier is stored where sign-in starts and ordinary PKCE completion requires the same browser/device. This would change cross-device email-link behavior. The current audit supplies no real GoTrue exchange proof, and mocked browser success would not establish that compatibility. Treat PKCE as a separately tested flow migration, not a checkbox needed to correct an overly broad allowlist. See [Supabase PKCE limitations](https://supabase.com/docs/guides/auth/sessions/pkce-flow) and [production redirect guidance](https://supabase.com/docs/guides/auth/redirect-urls), read during this review.

## Required release proof and limits

Native tests must cover anonymous/authenticated exact-link access, no default PUBLIC execution, no anonymous table or owner-column selection, owner-only authenticated table reads, revoked/unknown/malformed/non-Dogs cases, owner publish/update/revoke and denied foreign mutation. Include preservation of a legacy extra-key payload in storage while its public projection omits the extra key, and show both public grant forms are removed. Browser tests must cover signed-out and signed-in visitors, existing link routes, no Auth session adoption in either viewer, narrow pre-migration fallback and fail-closed error paths. A local database is meaningful grant/RLS evidence; it is not hosted JWT, PostgREST or Auth-delivery proof.

No customer rows, live Auth settings, live grants, credentials or hosted resources were changed by this independent review. Live SQL and Auth actions remain gated on exact approval. The original immutable audit is unchanged.
